# «Шкаф» — приложение для инвентаризации вещей и их хранения

**Статус:** утверждён (05.09.2026); расширен пользовательскими историями US-A…US-I и M8–M13 (07.09.2026); US-J (08.09.2026); US-K (09.09.2026); рекомендации ревью US-L…US-N и M14 (13.09.2026); финальная полировка US-L20–L22, риски, стек (14.09.2026); UX/UI-ревизия и консолидация ИИ US-O + M15 (19.09.2026)
**Платформа:** Android, minSdk 26 (Android 8.0), targetSdk 34
**Package:** `ru.vldkr.shkaff`

---

## 1. Задача

Упорядоченное хранение множества мелких вещей:
- учёт вещей: фото, номер/код, атрибуты, локация хранения;
- учёт систем хранения (шкафы, стеллажи) с фото и кликабельной разметкой ящиков/коробок;
- генерация штрихкодов/QR в виде картинок по шаблонам; поддержка номеров, написанных от руки;
- сканирование: камера смартфона (приоритет) + внешний USB/BT сканер;
- удаление фона на фото предмета (локально + опционально облако);
- экспорт базы в один файл (локально / сетевая папка / онлайн-хранилище);
- слияние двух баз с обработкой конфликтов;
- печать этикеток на 58-мм принтере (ESC/POS) — через приложение принтера (основной путь) или напрямую по Bluetooth / сети.

База данных проектируется с расчётом на рост функционала.

Расширенная дорожная карта — пользовательские истории (§2, US-A…US-O) и майлстоны M8–M15 (§10).

## 2. Пользовательские истории (US)

Приоритеты: **M** — Must, **S** — Should, **C** — Could. Порядок реализации — §10 (M8–M13).

### A. Быстрый ввод и массовые операции

**US-A1 · Массовый ввод однотипных объектов** — M
- На первом объекте серии галочкой «вводить для каждого» отмечаю изменяемые атрибуты; не отмеченные копируются из первого.
- Общие поля (название-паттерн, локация, категория, фото) префиллятся для всех следующих.
- Автонумерация (US-A2) продолжается по серии; в конце — список созданных и пачечная выдача этикеток.

**US-A2 · Автономера объектов любого уровня + немедленный QR** — M
- При создании storage / location / item присваивается уникальный номер: настраиваемый префикс + последовательность, раздельно по типу сущности (storage — `code`, location — `label`, item — `code`).
- Ручной номер остаётся возможен (override); дубликат блокируется (уникальный индекс на `item.code`).
- Кнопка «Выдать QR/этикетку» сразу после создания — рендер по шаблону, в галерею / печать.

**US-A3 · Справочники (категории и т.п.) — дополняемые inline** — M
- Справочники (select-атрибуты) редактируются прямо в форме объекта: «+ добавить значение» сразу пишет в словарь и подставляет.
- Справочник необязателен: объект сохраняется без значения.

**US-A4 · Черновик с автосохранением** — S
- Форма создания/редактирования автосохраняется черновиком (`draft`) на каждое действие.
- Черновик восстанавливается при повторном открытии; сбрасывается после успешного сохранения.

### B. Умный ввод вещи (EAN, LLM, фото)

**US-B1 · Скан рыночного штрихкода → заполнение из интернета** — S
- Считываю оригинальный EAN вещи; приложение запрашивает данные (OpenFoodFacts / UPCitemdb / GS1, при неудаче — LLM).
- Найденные поля сопоставляются с существующими атрибутами; недостающие предлагаются к добавлению в карточку **и** в словарь.
- В карточку попадают только подтверждённые пользователем поля.

**US-B2 · Поле «оригинальный штрихкод» (фото + числа)** — M
- В карточке вещи — поле `ean` (расшифровка числами) и/или фото штрихкода.
- Заполняется сканом (камера/внешний) или вручную; виден в карточке и в экспорте.

**US-B3 · LLM-агент (облако или локально, напр. Qwen)** — S
- Агент отвечает на вопросы («куда положить…», «что проверить…»), помогает упорядочить хранение и дозаполнить карточки, выступая инструкцией.
- Работает на контексте БД (категории, хранилища, объёмы, история).
- Режимы: облачный API (Qwen / OpenAI-compatible) по умолчанию, локальный (Ollama / на устройстве) — офлайн-фолбэк; переключатель в настройках.
- Индикатор режима в UI: 🟢 "Онлайн (Qwen API)" или 🟡 "Офлайн (Локальная модель)" (ревью, 14.09.2026).

**US-B4 · Поиск по фото через браузер** — C
- Кнопка «Найти в интернете» отправляет фото вещи в поиск по картинке (через браузер, напр. Yandex).
- Возврат в приложение; найденные атрибуты можно перенести в карточку.

### C. Иерархия, объём, масса, рекомендации

**US-C1 · Гибкая иерархия хранилищ** — S
- Базовая цепочка: город → склад → комната → шкаф → полка → коробка → пакет → объект.
- Уровни расширяемы вертикально и горизонтально (`level` на storage/location), но вложенность всегда однозначна и видна в UI — ни пользователь, ни приложение не путаются.
- Защита от циклической вложенности: валидация в DAO перед обновлением parentId (ревью, 14.09.2026).

**US-C2 · Визуализация хранилищ** — S
- Три режима: фото, загружаемое изображение, отрисовка стандартными блоками прямо в приложении.
- Кликабельные области (редактор разметки) работают поверх любого режима.

**US-C3 · Объём хранилищ** — S
- У хранилища задаётся ёмкость: коробка — внутренние Д×Ш×В, пакет/мешок — литры.
- Показ занятого (`currentVolume`) и остатка места после добавления объекта; предупреждение при превышении.

**US-C4 · Масса и грузоподъёмность** — S
- Хранилище накапливает массу вещей; опциональная грузоподъёмность (напр. пакет 25 кг) — нельзя нагрузить больше.
- Галочка «не заполнять до упора» — резерв места (удобно для поиска, чтобы не вываливалось).
- Пользователь может принудительно пометить хранилище «полное» — добавление блокируется (вручную или по лимиту).

**US-C5 · Температура и влажность** — C
- У хранилища атрибуты температуры и влажности; пока — ручной ввод.
- Позже — получение значений от датчиков по протоколу (MQTT/BLE, M13).

**US-C6 · Рекомендуемое хранилище при добавлении** — C
- По атрибутам, массогабаритам и заполненности программа предлагает хранилище с плюсами/минусами: объекты той же категории/аналоги, свободное место, близость к пользователю.
- Пользователь в начале работы указывает свою локацию — она участвует в ранжировании.

### D. Жизненный цикл вещи и напоминания

**US-D1 · Срок годности** — M
- У вещи — дата окончания срока годности (хранятся и продукты).
- Напоминание/подсветка скоро истекающих на дашборде и в карточке.

**US-D2 · Плановый осмотр / обслуживание** — S
- У вещи — дата планового осмотра (протереть, смазать, проверить герметичность) + заметка.
- Напоминание о наступлении срока.

**US-D3 · Временная выдача + напоминание о возврате** — S
- Вещь или хранилище можно пометить «выдано временно» (кому, когда, до когда).
- Приложение помнит активные выдачи и напоминает, что пора вернуть; действие «возврат» закрывает выдачу.

### E. Извлечение и группировка

**US-E1 · Корзина извлечения + алгоритм** — C
- Формирую список вещей для извлечения («корзина»).
- Приложение группирует действия по уровням: несколько предметов в одной коробке/локации — один шаг.
- Настройки сортировки: сначала хранилища с большим числом вещей из корзины; сначала мелкие предметы; по глубине вложенности; по близости к локации пользователя (набор расширяем).

**US-E2 · Стеки** — C
- Объединяю вещи и/или хранилища в стек — стек получает собственный дополнительный номер.
- Входящие объекты не теряют информацию и оригинальные номера: стек — дополнительный взгляд (группа), а не перенос.
- Комплекты/наборы («аптечка», «ремкомплект») — частный случай стека: скан QR набора → список входящих вещей; возвращённая вещь остаётся в наборе (ревью, 13.09.2026).

### F. Служебные QR и журнал

**US-F1 · Служебные QR-коды действий** — S
- QR кодирует действие: добавить хранилище / объект; переложить объект / хранилище; удалить объект / хранилище; временно передать объект / хранилище; экспортировать БД; импортировать БД; импортировать инкремент; распечатать последние N действий; показать/распечатать журнал пользователей; «скопировать отсканированный объект и выдать новый QR».
- Скан служебного QR на любом устройстве выполняет действие (с учётом прав профиля).

**US-F2 · Журнал действий** — S
- Приложение пишет журнал: кто (профиль), что (действие), над чем (объект/хранилище), когда, с какого устройства.
- Просмотр последних N, фильтр по типу/периоду, печать и экспорт.

### G. Пользователи, права, федерация БД

**US-G1 · Профили с разными правами** — S
- Выбор активного профиля при работе; права ограничивают действия.
- Пресеты: полный доступ (админ), только добавление в хранилища, только перекладка внутри хранилищ, только просмотр; состав расширяем.

**US-G2 · Админ-права и пир-синхронизация баз** — C
- Админ-права существуют в БД; можно подключить БД другого админа по LAN и синхронизироваться.
- Подключение необязательное и асимметричное: новая БД может быть присоединена без передачи прав на свою БД (флаги доверия в `peer_db`).

**US-G3 · Разделение / слияние БД по параметрам** — C
- Безопасный выгруз-фрагмент: только конкретные локации (или несколько), только объекты/хранилища за день/неделю/месяц.
- Фрагмент — валидная база; с общей базой (или другим фрагментом) снова склеивается без потерь.

### H. Экспорт

**US-H1 · Экспорт в xlsx и csv** — S
- Вся база хранения выгружается таблицами: вещи, хранилища, ящики; атрибуты — колонками.
- Форматы xlsx и csv; сохранение через SAF/Share.

### I. Новые требования (07.09.2026)

**US-I1 · Анализ объёма вещей агентом** — C
- Агент (US-B3) оценивает примерный объём списка вещей из контекста БД либо ищет точные габариты в интернете и предлагает их.
- По полученным объёмам — расчёт оставшегося места в хранилищах (в связке с US-C3: `currentVolume`/`capacityVolume`).
- Результат показывается пользователю как предложение; в БД пишется только после подтверждения.

**US-I2 · Экспорт без фото + восстановление фото при слиянии** — S
- На экране экспорта — галочка «без фото»: ZIP формируется без каталога `photos/`.
- Фрагмент, выгруженный без фото, при слиянии с полной базой получает фото своих объектов (фото — отдельный ресурс, восстанавливается по `entityId`).

**US-I3 · QR без приложения → установка** — C
- Служебный QR кодирует ссылку (`https://github.com/<org>/shkaff/…`): при установленном «Шкафе» — deep-link в приложение, при отсутствии — предложение скачать с GitHub.
- Скан такого QR на устройстве без приложения не падает — показывает ссылку/инструкцию.

**US-I4 · Система тегов** — S
- У вещи — несколько пользовательских тегов; словарь тегов дополняем прямо в поле («+ новый тег» сразу пишет в словарь).
- Фильтр и поиск по тегам; тег не обязателен.

**US-I5 · Камера как центр UX** — S
- Камера — главный вход: фото → приложение уточняет, что это (хранилище / объект / фото-атрибут, напр. штрихкод), и ведёт по сценарию.
- В карточке объекта у полей — кнопки «камера», «галерея», «ссылка — сохранить как картинку в базу».
- Картинка по ссылке скачивается и сохраняется в базе как фото (не ссылка в поле).

**US-I6 · Ручной макет этикетки** — C
- Помимо шаблонов — ручной макет: перетаскивание полей (QR, текст, логотип) на канве этикетки.
- Размер этикетки задаётся вручную; предпросмотр в мм (203 dpi) 1:1.

### J. Новые требования (08.09.2026)

**US-J1 · BLE-поиск Bluetooth-принтеров** — M
- «Найти по Bluetooth» ищет BLE-устройства как приложение «BLE Scanner»: многие 58-мм принтеры — BLE и не появляются в списке сопряжённых устройств.
- Результаты поиска: имя + MAC (или имя устройства, если MAC скрыт системой); выбрал устройство — сохранил как профиль принтера.
- Печать на BLE-принтер — ESC/POS через GATT (SPP-сервис `00001101-0000-1000-8000-0010AC510000`, характеристика `0x2901`); классический SPP — отдельный транспорт.

### K. Новые требования (09.09.2026)

**US-K1 · Каталог в стиле Ozon** — M (ключевая функция)
- Список вещей — каталог карточек, визуально повторяющий карточки товаров Ozon в приложении на Android: сетка карточек «фото / название / параметры», крупное фото, аккуратная типографика, привычный ритм маркетплейса.
- Карточка вещи (детальный экран) оформлена как страница товара Ozon: галерея фото сверху, название, ключевые атрибуты списком, описание — текстовым блоком как в описании товара.
- Это ключевая функция приложения: внешний вид каталога и карточки вещи — основной UX-ориентир.

### L. Полевые сценарии и массовые операции (ревью, 13.09.2026)

**US-L1 · Непрерывный скан («режим пулемёта»)** — S
- Камера висит в фоне; каждый считанный QR/штрихкод — бип + тактильный отклик; счётчик на экране: «Отсканировано: 14».
- В конце одним тапом — всё добавить в выбранное хранилище (однотипные объекты — US-A1; книги, болты, детали).
- Тактильная отдача: `HapticFeedbackConstants.CONFIRM` для успеха, `HapticFeedbackConstants.REJECT` для ошибки (ревью, 14.09.2026).

**US-L2 · Режим инвентаризации (audit)** — S
- «Сверить содержимое коробки B-14»: приложение показывает список того, что должно быть; пользователь просто сканирует вещи одну за другой.
- Звуковой сигнал + тактильный отклик: зелёный — вещь на месте, красный — не из этой коробки / не найдена.
- В конце — отчёт: «должно быть 10, отсканировано 8; не хватает: [список]; лишнее: [список]».
- Тактильная отдача обязательна для полевой работы (ревью, 14.09.2026).

**US-L3 · Табличный вид + массовые действия** — C
- Переключатель вида каталога «Карточки / Таблица»: плотная вёрстка, чекбоксы, массовые действия (выбрать N вещей → «Переместить в…», «Пометить тегом», «Печать этикеток»).
- Для power-юзеров: перемещение десятков вещей без пролистывания карточек.

**US-L4 · Жесты в каталоге** — C
- Свайп карточки влево — быстрое перемещение (выбор локации); вправо — быстрое редактирование / тег.
- Долгое нажатие — режим множественного выбора (как в галерее).

**US-L5 · Виджеты на главный экран Android** — C
- «Быстрый скан»: одна большая кнопка → сразу камера.
- «Скоро истечёт / требует внимания»: 3–5 позиций (US-D1, US-L9).
- «Недавние действия»: что добавлял/перемещал сегодня (из `action_log`).

**US-L6 · NFC-метки для контейнеров** — C
- Для хранилищ верхних уровней (коробки, ящики, шкафы) — NFC-метка NTAG213/215: приложил телефон → открылось содержимое, без прицеливания камерой.
- Мелкие вещи — остаётся QR (NFC-метки дороже).
- NDEF-запись — deep-link в приложение (совместимо с US-I3).

**US-L7 · Голосовой ввод и голосовой поиск** — C
- Кнопка микрофона в форме ввода: «добавь 10 саморезов по дереву в коробку Б-14» → LLM (US-B3) парсит интент и заполняет поля.
- Голосовой поиск: «где ключ на 12 и изолента?» → запрос к БД → ответ озвучивается (TTS): «ключ на 12 — в красном ящике, изолента — на верхней полке шкафа».

**US-L8 · Расходники и количество** — M
- Поля вещи: `quantity` (текущее количество, default 1), `unit` (шт/м/кг/л), `isConsumable`, `minQuantity?` (порог).
- Для расходника скан открывает не карточку, а экран «Приход/Расход»: быстрые +N/−N.
- `currentVolume`/`currentWeight` хранилища для расходников — пропорционально количеству и единице, а не поштучно.
- `quantity < minQuantity` → уведомление «пора купить изоленту».

**US-L9 · Гарантии и чеки** — S
- Поля вещи: `warrantyUntil?` (дата окончания гарантии), `receiptPhotoPath?` (фото чека в базе), `purchasePrice?` (цена покупки).
- OCR чека: фото бумажного чека → дата, магазин, товары, цены → привязать к существующей вещи (гарантия / доказательство покупки) или создать карточку.
- Дашборд: виджет «гарантия истекает через 30 дней» (в связке с US-D1).

**US-L10 · Финансовый дашборд + страховой экспорт** — C
- На главном — общая стоимость имущества (сумма `purchasePrice`), разбивка по хранилищам.
- Кнопка «Отчёт для страховой»: PDF с фото, описаниями, ценами и общей суммой (препперы, коллекционеры, загородные дома).

**US-L11 · Ассистент расхламления** — C
- Агент (US-B3) анализирует дату добавления и последнее касание (`action_log`): «вы не трогали эту вещь 2 года».
- Предлагает: продать (ссылка на объявление) / отдать / удалить; решение за пользователем.

**US-L12 · «Разбор бардака» по фото — пайплайн** — C
- LLM одна не понимает пространственных координат на фото; пайплайн:
  1. Object Detection (MediaPipe Object Detection или YOLO, TFLite/NCNN на устройстве) → bounding boxes объектов;
  2. для каждой маски — вырезка фрагмента;
  3. фрагмент → VLM (Qwen-VL / LLaVA, облако) с промптом «что это за предмет, название и категория»;
  4. приложение накладывает маски на фото — пользователь тапает, чтобы создать карточку.
- Шаги 1–2 — локально (MediaPipe предпочтительнее YOLO для Android — официальная оптимизация); VLM — облако (локальный VLM на мобиле слишком требователен) (ревью, 14.09.2026).

**US-L13 · Шаблонизация хранилищ** — C
- «Шаблон стеллажа»: фото + N кликабельных зон → применить к M однотипным хранилищам → M×N готовых ящиков с автонумерацией (US-A2).
- Не размечать каждый из 10 одинаковых стеллажей вручную.

**US-L14 · История перемещений вещи (timeline)** — S
- В карточке вещи — не только текущая локация, а таймлайн: «01.09.2026 → Коробка А; 15.09.2026 → Шкаф Б».
- Строится из `action_log` (action = move) — без новой сущности.

**US-L15 · Bluetooth-трекеры** — C
- Привязка внешнего трекера (AirTag / SmartTag / Mi) по ID к location/storage (ввод ID или скан QR с упаковки).
- «Коробка B-14 последний раз видна рядом с трекером в точке X» (данные — из приложения трекера; прямой доступ к AirTag без MFi невозможен).

**US-L16 · Bluetooth-весы** — C
- Коробка на весы → приложение по BLE считывает вес и вписывает в `currentWeight` хранилища (с подтверждением).
- Для складов и посылок.

**US-L17 · Публичные ссылки** — C
- Временная веб-ссылка на содержимое конкретной коробки («что в коробке с игрушками?») — отправить в мессенджер без установки приложения.
- Лёгкий web-эндпоинт или сгенерированная страница; ссылка одноразовая / со сроком — настраивается.

**US-L18 · Telegram-бот** — C
- Фото → черновик карточки; «где молоток?» → локация; бот присылает пуши о гарантии/сроках (US-D1, US-L9).
- Локальный бот на том же устройстве или облачный; опционально.

**US-L19 · Визуализация 2D/3D (долгосрок)** — C
- При известных габаритах комнаты/шкафов — простая 2D/3D-схема с кликабельными ящиками (маркетинговый фич-крючок, за пределами MVP).

**US-L20 · Статусы вещей (active, lent, disposed)** — S
- Поле `status` в item: `active` (в использовании), `lent` (выдано временно — US-D3), `disposed` (списано/утилизировано).
- Вещи со статусом `disposed` не участвуют в расчётах `currentVolume`/`currentWeight` хранилища, но остаются в БД для аудита и страховых отчётов (US-L10).
- Фильтр в каталоге: «Показать архив / списанное» (ревью, 14.09.2026).

**US-L21 · Undo для деструктивных действий** — S
- При удалении вещи, перемещении или массовых операциях — `Snackbar` с кнопкой «ОТМЕНИТЬ» на 5 секунд.
- Предотвращает фрустрацию и необходимость ручного отката через `action_log`.
- Применяется ко всем действиям, изменяющим структуру данных (ревью, 14.09.2026).

**US-L22 · Тактильная отдача при сканировании** — M
- Все операции сканирования (US-L1, US-L2, обычный скан) — обязательная тактильная отдача.
- `HapticFeedbackConstants.CONFIRM` — успешный скан, `HapticFeedbackConstants.REJECT` — ошибка/не та коробка.
- Критично для полевой работы в перчатках или при плохом освещении (ревью, 14.09.2026).

### O. Модернизация UX/UI и консолидация ИИ (19.09.2026)

**US-O1 · Онбординг + Camera-First дашборд** — S
- При первом запуске — 3-экранный онбординг: «Сфотографируйте — разберёмся» / «Всё по полочкам» / «ИИ поможет» → кнопка «Начать».
- После онбординга дашборд открывается сразу с камерой (раскрытие US-I5): наведи на штрихкод → автозаполнение (US-B1); наведи на предмет → фото → ИИ предлагает название и описание (US-O4); кнопка «Вручную» — классическая форма.
- Цель: время добавления первой вещи — с ~45 с до ~10 с.

**US-O2 · Мастер (wizard) как основной путь создания вещи** — S
- Основной путь создания — мастер (`ItemWizard`) вместо одной плоской формы (`ItemForm`): Шаг 1 — фото/скан; Шаг 2 — название + описание (только если ИИ не заполнил); Шаг 3 — где хранить (US-C6 + визуальный выбор); Шаг 4 — атрибуты (опционально, только релевантные).
- Автопропуск шагов, заполненных ИИ (confidence > 0.8); пользователь в любой момент может вернуться и поправить.
- Плоская форма остаётся для редактирования; мастер — для создания.

**US-O3 · Progressive disclosure в карточке вещи** — S
- Карточка (`ItemDetail`) — 3 уровня раскрытия: Essential (фото, название, локация, статус) → Extended (+описание, теги, атрибуты) → Full (+таймлайн US-L14, EAN, сырые данные).
- Кнопка «Показать все данные» / «Свернуть» переключает уровень; по умолчанию — Essential, чтобы casual-пользователь не видел 20+ полей.

**US-O4 · Единый ИИ-ассистент («умное заполнение»)** — S
- Вместо разрозненных ИИ-кнопок в форме («ИИ-подсказка», «Описание с ИИ», «Из ссылки», «Распознать скриншот») — одна кнопка «✨ Умное заполнение», сама выбирающая стратегию по контексту: фото → VLM (US-L12), ссылка → браузер (US-B4), EAN → каталоги (US-B1), текст → LLM (US-B3).
- Результат — набор предложений полей с confidence (US-O6); в карточку попадают только подтверждённые пользователем поля (принцип §3).
- Контекст — RAG (топ-N + структура хранилищ, §3), не полный дамп БД.

**US-O5 · Проактивные подсказки на дашборде** — C
- Дашборд сам предлагает действия (chips): «N вещей без ящика — разложить?», «N сроков истекают на этой неделе» (US-D1), «N вещей без этикетки — напечатать?».
- Источник — БД (`action_log`, `expirationDate`, этикетки), не LLM; ИИ (US-B3) — только для формулировок и приоритизации.

**US-O6 · Индикаторы уверенности ИИ + streaming UI** — S
- Каждое предложение ИИ — с confidence: >80% — primary + иконка «готово», 50–80% — tertiary, <50% — outline + «проверьте вручную».
- Потоковая генерация (`onToken`) видна пользователю (печатающийся текст / прогресс), а не «загрузка…»; режим LLM — индикатор онлайн/офлайн (§6.1).

**US-O7 · Fallback-цепочка автозаполнения** — S
- Единый порядок источников: локальная модель (если скачана, US-B3) → облачный API (ключ + сеть) → EAN (OpenFoodFacts/UPCitemdb, US-B1) → ручной ввод с подсказками из истории.
- Каждый уровень логируется; пользователь видит, откуда пришли данные (прозрачность, доверие).
- Обобщает US-B1/US-B3/US-B4 в один управляемый пайплайн.

**US-O8 · UX-полировка: skeleton, empty states, sealed UiState** — M
- Skeleton loading (shimmer, `rememberInfiniteTransition`) вместо `Text("Загрузка…")` в списках и карточках — без новых зависимостей.
- Actionable empty states: «Список пуст. [Добавить первую вещь]» вместо голого текста — на всех пустых экранах (вещи, хранилища, ящики).
- Sealed UiState (`Loading | Success | Error`) на каждый экран вместо набора `MutableStateFlow` (busy, error, step, isLoading…).
- Автофокус в формах; pull-to-refresh в каталоге.

**US-O9 · Material You (динамические цвета) + светлая тема** — C
- ⚠️ Конфликт с US-K1 (тёмный Ozon-вид — ключевая функция): Ozon-палитра остаётся базовой; Material You (API 31+, у нас minSdk 33) и светлая тема — опция-переключатель в Настройках, **не по умолчанию**.
- Включение по умолчанию — отдельное решение (§3).

**US-O10 · Type-safe навигация** — S
- Переход со строковых роутов на type-safe (Navigation 2.8.5 уже в стеке): `@Serializable`-маршруты + `toRoute<T>()`.
- Пререквизит: починка мёртвых роутов (`labels/…`, `templates`, `scan`, `annotations/…` — см. AGENTS.md), иначе навигация на них падает.
- Убирает класс runtime-ошибок «несуществующий маршрут».

**US-O11 · Predictive Back (Android 14+)** — C
- `android:enableOnBackInvokedCallback="true"` в манифесте (targetSdk 36 — доступно).
- Корректная обработка WindowInsets для `Scaffold` и клавиатуры (`Modifier.imePadding()`); edge-to-edge уже включён.

**US-O12 · Доступность (A11y)** — S
- Content description: осмысленные строки вместо `null` («Удалить <название>»).
- Минимальный тач-таргет 48 dp для всех IconButton/Chip (требование AGENTS.md).
- Shared element transitions (Compose 1.7+) — плавный переход фото из карточки в деталь.

**US-O13 · Hilt DI (опциональная миграция)** — C
- ⚠️ Конфликт с AGENTS.md («Нет Hilt и другого DI», ручной синглтон `Deps`): решение о миграции — до начала M15.
- Если принято: постепенный переход — сначала ViewModel-слой (domain/чистый Kotlin остаётся без DI), без big-bang.
- Если не принято: фиксируем «не делаем» в §3, история снимается.

```
loan             id, entityType (item|storage), entityId → item/storage,

action_log       id, userId → user, action (add|move|delete|lend|return|export|import|…),
                 entityType, entityId, detail JSON, at, deviceId

stack            id, name, code (автонумер),
                 createdAt, updatedAt, deletedAt, deviceLastModified
stack_member     id, stackId → stack, entityType (item|storage), entityId, sortOrder
                 (члены сохраняют свою идентичность и оригинальные номера)

peer_db          id, peerDeviceId, trust JSON (области и права пира), lastSyncedAt,
                 createdAt, updatedAt, deletedAt

sensor           id, storageId → storage, protocol (manual|mqtt|ble), address,
                 lastTemp, lastHumidity, lastAt, updatedAt

tracker          id, name, kind (airtag|smarttag|mi|other), externalId (UUID трекера),
                 storageId? / locationId? (привязка к контейнеру),
                 lastSeenAt?, note, updatedAt

draft            id, entityType, entityId?, formJson, savedAt
                 (черновик формы — автосохранение на каждое действие)

item_attributes_fts  item_id, text_content
                     (FTS5 виртуальная таблица для быстрого поиска по значениям атрибутов;
                      синхронизируется триггером или в Repository при сохранении item) (ревью, 14.09.2026)
```

Почему так:
- **Атрибуты**: JSON на сущности + словарь `attribute_def` + FTS5-индекс → новые атрибуты без миграции, UI рисует типизированные поля, фильтры работают быстро через `item_attributes_fts` (ревью, 14.09.2026).
- **Нормализованные координаты аннотаций** — подписи не смещаются при смене разрешения фото.
- **Вложенные locations** — иерархия хранения без новых сущностей.
- **FTS5** по `name/description/code` + `item_attributes_fts` — быстрый поиск (ревью, 14.09.2026).
- **Room migrations** + `schema_meta.schemaVersion` — безопасный рост.
- **Автономера**: prefix+seq раздельно по типу сущности (счётчики в `schema_meta`); ручной override сохраняется.
- **Заполненность**: `capacity*` — заявленный лимит, `current*` — сумма от содержимого; `dontFillToBrim` резервирует долю, `isFull` — жёсткая блокировка добавления; вещи со статусом `disposed` не учитываются в `current*` (ревью, 14.09.2026).
- **Стеки** — отдельный взгляд на вещи/хранилища в группах, без переноса и потери оригинальных номеров.
- **Профили / журнал / выдачи** — аудит и права без учётных записей: локальные именованные профили.

## 6. Экраны и сценарии

### Экраны
1. **Главная** — статистика (вещи/ящики/шкафы), поиск, глобальная кнопка скана.
2. **Хранилища** — список; добавление с атрибутами (по словарю).
3. **Хранилище** — фото с кликабельной разметкой ящиков; список ящиков; действия.
4. **Ящик (location)** — вещи внутри, фото ящика, атрибуты, этикетка.
5. **Вещь (item)** — фото (оригинал/вырезка), код, атрибуты, локация, этикетка, действия, статус (active/lent/disposed).
6. **Шаблон этикеток** — создание/редактирование, предпросмотр, генерация PNG.
7. **Принтеры** — профили, поиск по сети/BT, тестовая печать.
8. **Импорт/Экспорт** — сохранение/выбор файла, запуск слияния.
9. **Конфликты** — разрешение по записям и по полям.
10. **Настройки** — deviceId, облачный API ключ фона, сканер (prefix/suffix), тема.
11. **Массовый ввод** — серия однотипных объектов: галочки «вводить для каждого», автонумерация, пачечные этикетки.
12. **Профили** — выбор активного профиля; роли и права (админ / добавление / перекладка / просмотр).
13. **Выдача** — временная передача вещи/хранилища (кому, срок), активные выдачи, напоминания, возврат.
14. **Журнал** — последние N действий (кто/что/когда), фильтр, печать/экспорт.
15. **Служебные QR** — генерация QR-действий и их выполнение по скану.
16. **Корзина извлечения** — список вещей к извлечению, алгоритм по уровням, настройки сортировки.
17. **Стеки** — создание/редактирование стека (номер, состав), вид группы.
18. **Агент (LLM)** — диалог: подбор места, дозаполнение карточки, подсказки; режим «облако / локально» + индикатор статуса (онлайн/офлайн).
19. **Табличный экспорт** — xlsx/csv (вещи/хранилища/ящики), атрибуты колонками.
20. **Федерация** — пир-базы: подключение по LAN, область и права, синхронизация.
21. **Каталог (US-K1)** — список вещей сеткой карточек в стиле Ozon (фото / название / параметры); карточка вещи (п. 5) — как страница товара Ozon: галерея фото, название, ключевые атрибуты, описание текстовым блоком.
22. **Режим инвентаризации (US-L2)** — сверка содержимого локации: список «что должно быть», скан + бип + тактильный отклик, отчёт «не хватает / лишнее».
23. **Непрерывный скан (US-L1)** — камера в фоне, бип + тактильный отклик на каждый код, счётчик, одним тапом — добавить всё в выбранное хранилище.
24. **Табличный вид (US-L3)** — плотный список вещей с чекбоксами и массовыми действиями (переместить / теги / этикетки).
25. **Финансовый дашборд (US-L10)** — общая стоимость, разбивка по хранилищам, «отчёт для страховой» (PDF).
26. **Онбординг (US-O1)** — 3 экрана при первом запуске («Сфотографируйте» / «Всё по полочкам» / «ИИ поможет»); после — Camera-First дашборд (US-I5) с проактивными подсказками (US-O5).

### Ключевые сценарии
1. **Хранилище:** добавить → атрибуты → фото → **редактор разметки**: тап создаёт прямоугольник; перетаскивание/уголки; подпись «B-14»; цвет. Области кликабельны — тап открывает ящик.
2. **Вещь:** в ящик добавить вещь → фото → номер (ручной ввод / генератор: prefix+seq / рандом) → атрибуты → статус (default active).
3. **Этикетка:** шаблон → рендер QR/CODE128 (203 dpi) → PNG → галерея / печать / Share.
4. **Скан:** камера (CameraX + ML Kit) — приоритет; USB/BT HID-сканеры — перехват быстрого ввода в активное поле + настройка отбрасывания суффиксов (Enter и т.п.); ручной ввод — fallback. Скан с главной сразу открывает вещь/ящик.
5. **Удаление фона:** кнопка на фото вещи → локальная TFLite-модель (качается один раз, ~40–80 МБ, прогресс) → PNG с альфой; опционально облачный API по ключу. Оригинал и вырезка хранятся рядом, переключаются.
6. **Экспорт:** один ZIP → локальная папка / SAF (SMB, OneDrive, Dropbox, Drive) / Share.
7. **Слияние:** импорт ZIP → движок → при конфликтах — экран разрешения.
8. **Массовый ввод:** «N однотипных» → первый объект + галочки «вводить для каждого» → серия с автонумерацией → пачка этикеток.
9. **Выдача:** вещь/хранилище → «Выдать» (кому, срок) → напоминание о возврате → «Возврат» (статус вещи меняется обратно на active).
10. **Служебный QR:** сгенерировать QR-действие (напр. «переложить в B-14») → напечатать → отсканировать → действие с учётом прав профиля.
11. **Извлечение:** отметить вещи в «корзину» → «Сформировать алгоритм» → шаги, сгруппированные по хранилищам → выполнение по чек-листу.
12. **Агент:** «Куда положить дрель?» → топ-кандидаты с плюсами/минусами; «Заполни карточку» → предложенные поля из интернета/LLM.
13. **Пир-синхронизация:** добавить пир по LAN → область и права → синхронизация → запись в журнал.
14. **Каталог (US-K1):** главная → «Каталог» — сетка карточек как в Ozon → тап по карточке → карточка вещи как страница товара Ozon (галерея, название, атрибуты, описание) → действия (этикетка, локация, фото).
15. **Расходник (US-L8):** скан изоленты → экран «Приход/Расход» → «−2 м» → количество 8 м; ниже порога — уведомление «пора купить».
16. **Инвентаризация (US-L2):** «Сверить B-14» → сканирую вещи подряд (бип + тактильный отклик) → отчёт: «должно 10, отсканировано 8, не хватает: [2 позиции]».
17. **Непрерывный скан (US-L1):** включаю режим → камера в фоне → бип + тактильный отклик на каждый код → «Отсканировано: 14» → тап «Добавить в B-14».
18. **Голосом (US-L7):** «Добавь 10 саморезов по дереву в коробку Б-14» → поля формы заполнены агентом → «Сохранить».
19. **Списание (US-L20):** вещь → «Списать/Утилизировать» → статус меняется на `disposed` → вещь не удаляется, но не учитывается в заполненности хранилища → доступно в фильтре «Архив».
20. **Undo (US-L21):** удаление вещи → Snackbar «Вещь удалена. ОТМЕНИТЬ» (5 сек) → тап на «ОТМЕНИТЬ» → вещь восстановлена.

## 7. Печать (58 мм, ESC/POS)

Два слоя (адаптерный дизайн):

1. **Гарантированный путь:** этикетка → PNG (203/300 dpi) → галерея + системная Share → приложение принтера.
2. **Прямое подключение (экран «Принтеры»):**
   - **Сеть:** mDNS-обнаружение + ручной ввод `IP:9100`; raw TCP-сокет.
    - **Bluetooth:** классический SPP (RFCOMM, канал 1); список устройств, запрос сопряжения, фильтр по имени.
    - **BLE (US-J1):** поиск устройств как «BLE Scanner» (`BluetoothLeScanner`) — BLE-принтеры не видны в списке сопряжённых; печать — ESC/POS через GATT (SPP-сервис `0x1101`), отдельный транспорт `ble`.
   - **Профиль принтера в БД** (`printer_profile`): транспорт, адрес, ширина 58 мм, смещения; тестовая печать.
    - **Протокол:** ESC/POS, raster-вставка `GS v 0` (bit image), команды `GS h` (двойной размер), обрезка по ширине.
    - **Производительность (ревью):** текст — векторные команды `ESC !`, штрихкод — `GS k`; растром (`GS v 0`) — только логотип/фото, иначе печать на 58-мм занимает 10–15 с.
    - **Дизеринг (ревью):** фото/логотип конвертируем в 1-bit с дизерингом Флойда–Штейнберга, иначе на термопринтере — чёрное пятно.

Рендер строго **203 dpi (8 dot/mm)**: 58 мм = 464 px, 40 мм = 320 px. Размеры задаются на шаблон.

Разрешения: `BLUETOOTH_CONNECT`, `BLUETOOTH_SCAN` (Android 12+), `BLUETOOTH/BLUETOOTH_ADMIN` (<12), `INTERNET`, `ACCESS_NETWORK_STATE`; геолокация — для BT discovery до Android 11 и для MAC в результатах BLE-поиска на Android 12+ (US-J1).

Структура: `domain/printer/` → `LabelRenderer` (мм→px), `PrintJob`, `Transport` (interface: `ShareTransport`, `TcpTransport`, `BtSppTransport`), `EscPosProtocol`.

## 8. Экспорт / слияние баз

### Формат экспорта (один файл)
ZIP:
```
manifest.json          { schemaVersion, deviceId, lastSyncWatermark,
                         storage[], location[], item[], annotation[],
                         label_template[], attribute_def[], printer_profile[] }
photos/                <entityId>_<kind>.<ext>
```
JSON (не сырой SQLite) — независимость от версий БД при росте.

Опция «экспорт без фото» (US-I2): ZIP без каталога `photos/`; при слиянии с полной базой фото восстанавливаются по `entityId`.

### Сохранение
- локальная папка (SAF);
- сетевая папка (SMB) и онлайн-хранилища (OneDrive/Dropbox/Drive) — как SAF-каталоги;
- системный Share.

### Алгоритм слияния (2-way, offline-first)
1. Базы A (локальная) и B (импорт). `lastSyncWatermark` из последнего успешного мержа определяет «изменилось с обеих сторон».
2. По каждой сущности (по UUID):
   - только в A → оставить;
   - только в B → вставить;
   - обе живые:
     - содержимое идентично → ничего;
     - изменилась только одна (по `updatedAt` vs watermark) → берём её (LWW);
     - изменились **обе** → очередь конфликтов.
   - tombstone (удалена с одной стороны) vs изменение с другой → конфликт «удалено/изменено».
3. **Конфликт-экран:** две карточки бок о бок; «всё из A/B» или **поле за полем** (имя, локация, атрибуты, фото — для фото показываем оба, выбираем одно). Решения пишутся в `conflict_log`.
4. **FK-консистентность:** вещь без ящика → «без локации» (с уведомлением); ящик без шкафа → наверх (с подтверждением).
5. **«Удалено vs изменено» — всегда вручную (ревью):** LWW не «воскрешает» удалённую вещь; перемещение на другом устройстве не отменяет удаление без подтверждения.
6. **Коллизия автонумеров (ревью):** одинаковый `code`/`label` при разных UUID → перегенерация номера импортированной сущности (префикс + новый seq) + запись в `conflict_log` («автонумер X изменён на Y из-за коллизии при слиянии»).
7. **Удаление location (ревью):** вещи внутри не удаляются — `locationId = null`; заметный диалог: «Внутри 15 вещей. Они останутся без локации. Продолжить?».
8. После мержа `lastSyncWatermark = now`.

Движок — чистый Kotlin, полный набор юнит-тестов: LWW, обе изменены, tombstone vs изменение, переезд вещи, вложенность, идентичные записи.

| Риск | Мера |
|---|---|
| HID-сканеры передают разные суффиксы | Настройки prefix/suffix; тест на реальном сканере (M3) |
| mDNS у 58-мм принтеров часто отсутствует | Ручной ввод `IP:9100` обязателен (M7) |
| u2net на слабых телефонах 1–3 с/фото | Прогресс-индикатор, кэш результата, фоновый поток |
| Merge — самый сложный блок | Движок и тесты пишутся первыми внутри M6 |

| Рост функционала ломает БД | Room-миграции + schemaVersion в manifest экспорта |
| LLM на слабых устройствах / офлайн | облако по умолчанию + локальный фолбэк (Ollama / LiteRT-LLM), кэш ответов, фоновый поток |
| Точность EAN-данных из интернета | только подтверждённые пользователем поля попадают в карточку/словарь |
| Пир-синхронизация: права и конфликты | флаги доверия в `peer_db`, область синхронизации по узлам, LWW + conflict_log |
| Черновики и журнал раздувают БД | периодическая очистка `draft`/`action_log`, индексы по entityId |
| JSON-атрибуты: фильтры — full table scan (10k+ вещей) | Гибрид: JSON на сущности + FTS5-виртуальная таблица `item_attributes_fts` для быстрого поиска; решить до M8 (§3) |
| LLM: вся БД не помещается в контекст | RAG: до запроса — поиск топ-N (10–20) релевантных записей в промпт + структура хранилищ (US-B3) |
| LWW: «удалено vs изменено» воскрешает удалённую вещь | всегда ручной конфликт; удаление имеет приоритет (§8, п. 5) |
| Размер фото: JPEG 85 @1600px ≈ 300–500 КБ × 1000 вещей | WebP lossy ~80 (100–150 КБ), Coil читает нативно (§3) |
| ESC/POS raster медленный на 58-мм (10–15 с) | текст/штрихкод — векторные `ESC !`/`GS k`; растр — только логотип; дизеринг Флойда–Штейнберга (§7) |
| Коллизия автонумеров при мерже (одинаковый code, разные UUID) | перегенерация номера импортированной сущности + `conflict_log` (§8, п. 6) |
| SAF медленный/глючный на SMB и облаках | fallback `ACTION_OPEN_DOCUMENT_TREE`; тест на реальном Wi-Fi роутере с SMB (M6); прогресс-бар с текстом «Подготовка файла...» (ревью, 14.09.2026) |
| LLM на устройстве: «сырой» Qwen через TFLite — больно (токенизатор) | обёртки LiteRT-LLM / llama.cpp (JNI) (§4) |
| LLM не понимает пространственных координат на фото | пайплайн MediaPipe Object Detection (или YOLO/SAM, TFLite/NCNN) → маски → VLM (облако) для названий (US-L12) |
| Циклическая вложенность хранилищ | Валидация в DAO перед обновлением parentId: новый родитель не должен быть потомком текущей сущности (US-C1, ревью, 14.09.2026) |
| Фоновые задачи убиваются Android Doze mode | Для длительных операций (обработка пачки фото, LLM-запросы, синхронизация) использовать `WorkManager` с `ForegroundService` + персистентное уведомление (ревью, 14.09.2026) |
| Права доступа Android 13/14 запрашиваются агрессивно | Контекстные запросы: `POST_NOTIFICATIONS` — только при настройке напоминания, `READ_MEDIA_IMAGES` — только при первом нажатии «Галерея»; обработать сценарий «Не спрашивать снова» (ревью, 14.09.2026) |
| БД фрагментируется при активной работе | Фоновая задача раз в неделю: `PRAGMA optimize` + `VACUUM` + очистка старых `action_log` (>1 года) и завершённых `draft` (§3, ревью, 14.09.2026) |
| Material You (динамические цвета) ломает Ozon-вид — ключевую функцию US-K1 | Ozon-палитра остаётся базовой; Material You + светлая тема — только опция в Настройках, не по умолчанию (US-O9, ревью, 19.09.2026) |
| Type-safe навигация затрагивает все экраны (риск регрессий) | Пошагово: сначала починить мёртвые роуты, затем вводить type-safe маршруты экран за экраном; прогон навигации по всем экранам после каждого шага (US-O10) |
| Hilt конфликтует с ручным `Deps` (AGENTS.md: «Нет Hilt и другого DI») | Решение до M15: либо постепенная миграция (сначала ViewModel-слой), либо фиксация «не делаем» в §3 (US-O13) |

## 6.1. UX/UI гайдлайны (ревью, 14.09.2026)

### Тактильная отдача (Haptic Feedback)
Все операции сканирования (US-L1, US-L2, обычный скан с камеры) — обязательная тактильная отдача:
- `HapticFeedbackConstants.CONFIRM` — успешный скан (зелёный бип).
- `HapticFeedbackConstants.REJECT` — ошибка/не та коробка (красный бип).
- Критично для полевой работы в перчатках или при плохом освещении.

### Undo для деструктивных действий
При удалении вещи, перемещении или массовых операциях (US-L3):
- `Snackbar` с кнопкой «ОТМЕНИТЬ» на 5 секунд.
- Предотвращает фрустрацию и необходимость ручного отката через `action_log`.
- Применяется ко всем действиям, изменяющим структуру данных.

### Индикатор режима LLM
В интерфейсе агента (US-B3) — индикатор статуса:
- 🟢 "Онлайн (Qwen API)" — быстрый ответ.
- 🟡 "Офлайн (Локальная модель)" — медленнее, но работает без интернета.
- Пользователь понимает, почему агент отвечает 10 секунд или не работает.

### Контекстные запросы разрешений
Не запрашивать все разрешения при первом запуске:
- `POST_NOTIFICATIONS` (Android 13+) — только когда пользователь впервые настраивает напоминание о гарантии.
- `READ_MEDIA_IMAGES` — только при первом нажатии кнопки «Галерея».
- Обязательно обработать сценарий «Не спрашивать снова» — показать экран с инструкцией, как включить в настройках.

### Skeleton loading (ревью, 19.09.2026)
Вместо `Text("Загрузка…")` — skeleton-карточки (shimmer через `rememberInfiniteTransition`):
- Список вещей: skeleton = фото 1:1 + две строки текста.
- Детальный экран: skeleton-секции по структуре карточки.
- Без новых зависимостей (US-O8).

### Progressive disclosure (ревью, 19.09.2026)
Карточка вещи — 3 уровня: Essential (фото/название/локация/статус) → Extended (+описание, теги, атрибуты) → Full (+таймлайн, EAN, сырые данные). По умолчанию — Essential, переключение кнопкой «Показать все данные» / «Свернуть» (US-O3).

### Unified AI + confidence (ревью, 19.09.2026)
Одна кнопка «✨ Умное заполнение» вместо 4+ ИИ-кнопок; сама выбирает источник (фото → VLM, ссылка → браузер, EAN → каталоги, текст → LLM). Каждое предложение — с индикатором уверенности: >80% — «готово», 50–80% — «проверьте», <50% — «вероятно, вручную» (US-O4, US-O6).

### Actionable empty states (ревью, 19.09.2026)
Пустые экраны — с кнопкой действия: «Список пуст. [Добавить первую вещь]», «Нет хранилищ. [Создать шкаф]» — вместо голого текста (US-O8).

### Sealed UiState (ревью, 19.09.2026)
Каждый экран — одно состояние `Loading | Success | Error` вместо набора `MutableStateFlow` (busy, error, step, isLoading…); упрощает ViewModel и исключает «невозможные» состояния (US-O8).
